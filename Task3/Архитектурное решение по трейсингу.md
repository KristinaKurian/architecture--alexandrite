# Архитектурное решение по трейсингу

## 1. Анализ системы

Заказ в «Александрите» проходит через несколько приложений и асинхронных интеграций:

```text
B2C:
Пользователь
    ↓
Online Shop
    ↓
MES
    ↓
RabbitMQ
    ↓
CRM
    ↓
MES
    ↓
CRM

B2B:
Partner API
    ↓
MES
    ↓
RabbitMQ
    ↓
CRM
    ↓
MES
```

При существующей архитектуре нет единого механизма, позволяющего ответить на вопросы:

- где сейчас находится конкретный заказ;
- какой сервис последним успешно обработал заказ;
- какое сообщение было отправлено в RabbitMQ;
- получил ли его consumer;
- сколько времени занял каждый этап;
- произошла ли ошибка;
- была ли повторная обработка;
- какой именно запрос или событие привели к изменению состояния заказа.

Особенно критично это из-за того, что часть взаимодействия MES и CRM выполняется асинхронно через RabbitMQ.

---

# 2. Системы, которые необходимо покрыть трейсингом

## 2.1. Online Shop Backend

Необходимо трассировать:

- создание заказа;
- загрузку/создание 3D-модели;
- перевод в `SUBMITTED`;
- вызов MES;
- получение результата расчёта стоимости.

Возможные проблемы:

- запрос не дошёл до MES;
- MES вернул ошибку;
- timeout;
- заказ сохранился в Shop, но дальнейшая обработка не началась.

---

## 2.2. Partner API / внешний API MES

Это наиболее критичная точка после открытия B2B API.

Необходимо трассировать:

- приём запроса;
- создание заказа;
- передачу задания на расчёт;
- результат обработки;
- ошибки и retries.

---

## 2.3. MES

MES является центральной частью order flow.

Необходимо трассировать:

- получение заказа;
- запуск расчёта стоимости;
- завершение расчёта;
- переход в `PRICE_CALCULATED`;
- публикацию сообщения в RabbitMQ;
- получение команд из CRM;
- `MANUFACTURING_STARTED`;
- `MANUFACTURING_COMPLETED`;
- `PACKAGING`;
- `SHIPPED`.

Также необходимо отдельно измерять длительный расчёт стоимости, который может занимать до 30 минут.

---

## 2.4. RabbitMQ

Для messaging необходимо обеспечить propagation trace context.

Трассируется логическая цепочка:

```text
MES
 ↓
publish
 ↓
RabbitMQ
 ↓
consume
 ↓
CRM
```

Необходимо видеть:

- кто опубликовал сообщение;
- какой `event_id` был отправлен;
- какая queue использовалась;
- когда consumer получил сообщение;
- была ли повторная доставка;
- произошла ли ошибка обработки.

---

## 2.5. CRM

Необходимо трассировать:

- создание заказа после сообщения MES;
- обработку события `PRICE_CALCULATED`;
- переход в `MANUFACTURING_APPROVED`;
- отправку команд/событий MES;
- перевод заказа в `CLOSED`.

---

## 2.6. Object Storage

Не требуется создавать span на каждую внутреннюю операцию Object Storage.

Но необходимо создавать client span со стороны вызывающего приложения для операций:

```text
upload model
download model
read model
```

Это позволит определить, например, что MES завис не на расчёте, а на загрузке 3D-файла.

---

## 2.7. Внешняя транспортная компания

Если транспортная компания находится вне инфраструктуры «Александрита», внедрить туда OpenTelemetry невозможно.

На нашей стороне трассируем:

- outbound request;
- inbound callback;
- HTTP status;
- latency;
- ошибки.

---

# 3. Места возможного зависания заказа

Критический путь:

```text
INITIATED
    ↓
FILE_UPLOADED
    ↓
SUBMITTED
    ↓
PRICE_CALCULATED
    ↓
MANUFACTURING_APPROVED
    ↓
MANUFACTURING_STARTED
    ↓
MANUFACTURING_COMPLETED
    ↓
PACKAGING
    ↓
SHIPPED
    ↓
CLOSED
```

Необходимо контролировать каждый переход.

Особенно критичны:

```text
SUBMITTED
    ↓
PRICE_CALCULATED
```

поскольку расчёт может занимать до 30 минут, и:

```text
PRICE_CALCULATED
    ↓
RabbitMQ
    ↓
CRM
    ↓
MANUFACTURING_APPROVED
```

поскольку здесь присутствует асинхронная интеграция.

# 4. Данные, которые должны попадать в tracing

Для каждого span необходимо передавать стандартные технические поля:

```text
trace_id
span_id
parent_span_id
service.name
service.version
deployment.environment
span.name
start_time
end_time
duration
status
error.type
```

Для HTTP:

```text
http.request.method
http.route
http.response.status_code
server.address
```

Для RabbitMQ:

```text
messaging.system = rabbitmq
messaging.destination.name
messaging.operation
messaging.message.id
```

Для бизнес-процесса:

```text
order.id
correlation.id
event.id
order.source = b2b | b2c
order.status.from
order.status.to
operation
retry.count
```

Например:

```text
trace_id = 9fd...
service.name = mes
span.name = order.calculate_price

order.id = 12345
correlation.id = abc-001
order.source = b2b

order.status.from = SUBMITTED
order.status.to = PRICE_CALCULATED

duration = 178s
status = OK
```

---

# 5. Что не следует помещать в tracing

В spans нельзя помещать:

- содержимое 3D-файла;
- ФИО;
- телефон;
- email;
- адрес доставки;
- платёжные данные;
- access token;
- Authorization header;
- пароли;
- RabbitMQ credentials;
- полный request/response body.

Для расследования достаточно технических идентификаторов.

---

# 6. Особенность длительного жизненного цикла заказа

Один заказ может обрабатываться несколько недель.

Создавать один гигантский OpenTelemetry trace длительностью три недели нецелесообразно.

Поэтому предлагается использовать два уровня корреляции.

## Технический trace

Описывает одну связанную техническую операцию:

```text
HTTP request
    ↓
MES
    ↓
RabbitMQ publish
```

или:

```text
RabbitMQ consume
    ↓
CRM
    ↓
DB
```

## Business correlation

Все traces одного заказа связываются через:

```text
order.id
correlation.id
event.id
```

В результате по `order.id=12345` можно найти все traces, относящиеся к заказу, даже если они выполнялись в разные дни.

---

# 7. Мотивация

Сейчас команда узнаёт о проблемах в основном после обращения клиента.

Distributed tracing позволит видеть полную цепочку прохождения запроса и события между сервисами.

Например:

```text
Partner API       OK       120 ms
       ↓
MES               OK       250 ms
       ↓
Price Calculation OK       175 sec
       ↓
RabbitMQ publish  OK       10 ms
       ↓
CRM consume       ERROR    timeout
```

Из такой трассы сразу понятно, что расчёт успешно завершился, но CRM не смог обработать сообщение.

Без tracing команда может потратить часы на проверку нескольких приложений.

# 8. Метрики, на которые повлияет внедрение tracing

## 8.1. Mean Time To Detect — MTTD

Время между появлением проблемы и её обнаружением должно уменьшиться.

---

## 8.2. Mean Time To Repair — MTTR

Инженеру не требуется вручную собирать информацию из нескольких систем.

По `order.id` или `trace_id` можно сразу определить место ошибки.

---

## 8.3. Время поддержки одного обращения

Должно снизиться среднее время расследования жалобы клиента.

---

## 8.4. Количество зависших заказов

После добавления автоматического контроля trace data зависшие order flows должны обнаруживаться раньше.

---

## 8.5. Процент заказов с полностью восстанавливаемой историей

Можно ввести внутренний показатель:

```text
trace_coverage_percent
```

Целевое значение для критического order flow:

```text
> 99%
```

# 11. Передача trace context через RabbitMQ

HTTP автоматически поддерживает передачу trace context через headers.

Для RabbitMQ необходимо передавать W3C trace context в message headers.

Например:

```text
traceparent
tracestate
```

Дополнительно:

```text
x-correlation-id
x-event-id
x-order-id
```

Consumer извлекает контекст и создаёт следующий span.

Таким образом:

```text
MES producer span
        ↓
 RabbitMQ message
        ↓
CRM consumer span
```

оказываются логически связанными.

---

# 12. OpenTelemetry Collector

Collector предлагается разместить внутри private network.

Он будет:

- принимать OTLP;
- выполнять batching;
- filtering;
- sampling;
- удалять запрещённые attributes;
- экспортировать traces в Data Prepper;
- формировать derived metrics.

Приложения не должны напрямую писать в OpenSearch.

---

# 13. Хранилище и визуализация

Для хранения tracing data предлагается использовать Yandex Managed Service for OpenSearch.

Data Prepper преобразует OpenTelemetry traces в формат Trace Analytics.

В OpenSearch Dashboards инженер сможет:

- найти trace;
- найти traces по `order.id`;
- посмотреть service map;
- определить error spans;
- увидеть latency;
- определить проблемный сервис.

---

# 14. Sampling

Для обычного production traffic не обязательно хранить 100% traces бесконечно.

Предлагается:

```text
ERROR traces                 → 100%
slow traces                  → 100%
B2B order critical flow      → 100% на первом этапе
обычные успешные requests    → sampling
```

На начальном этапе внедрения критический путь заказа лучше трассировать полностью.

После измерения реального объёма можно уменьшить sampling успешных технических запросов.

# 16. Автоматический контроль прохождения заказа

## Дополнительное задание

Одного интерфейса для ручного поиска traces недостаточно.

Необходимо автоматически определять зависшие процессы.

Предлагается добавить:

```text
Order Flow Monitor
```

Он периодически анализирует trace data и проверяет максимальное время нахождения заказа на критических этапах.

Например:

```text
SUBMITTED
→ PRICE_CALCULATED

нормально:
до 30 минут

превышение:
> 30–45 минут
```

или:

```text
PRICE_CALCULATED
→ MANUFACTURING_APPROVED

нормально:
несколько минут

превышение:
> установленного SLO
```

---

## 16.1. Derived metrics

Из tracing data формируются:

```text
order_transition_duration_seconds
trace_errors_total
stuck_orders_total
service_dependency_errors_total
```

Важно:

`order_id` не используется как label metrics.

Он остаётся только в trace store.

Metrics используют низкокардинальные labels:

```text
status
source
service
environment
```

---

## 16.2. Alerting

Derived metrics отправляются в Prometheus/Yandex Monitoring.

Например:

```text
stuck_orders_total{
    status="SUBMITTED"
} > 0
```

→ Warning.

Большое количество зависших заказов:

```text
stuck_orders_total > threshold
```

→ Critical.

Alert содержит:

```text
status
service
dashboard link
trace search link
```

# 18. Компромиссы

## Стоимость хранения

Tracing создаёт значительный объём данных.

Чем больше:

- RPS;
- spans;
- attributes;
- retention,

тем дороже хранение.

Для снижения стоимости применяется sampling и ограничение retention.

---

## Tracing не заменяет messaging reliability

Наличие trace покажет:

```text
сообщение потерялось
```

но само по себе не гарантирует доставку сообщения.

Для надёжности всё равно необходимы:

- transactional outbox;
- publisher confirms;
- retry;
- DLQ;
- idempotency.

---

## Tracing не заменяет logging

Trace хорошо показывает:

```text
где произошла ошибка
```

но подробная информация об exception находится в logs.

Поэтому необходимо связывать:

```text
trace_id
span_id
```

с логами.

---

## Ограничения внешних систем

Если транспортная компания не поддерживает tracing, внутри её инфраструктуры цепочка будет недоступна.

Можно увидеть только:

```text
наш outbound request
и
их inbound callback
```

---

## Legacy MES

Хотя исходный код MES доступен, его существенная инструментализация может потребовать времени разработчика на C#.

Поэтому начинать следует с:

- HTTP;
- RabbitMQ;
- ключевых business operations.

---

## Длительные бизнес-процессы

Distributed trace плохо подходит как один trace для процесса длительностью несколько недель.

Поэтому технические traces объединяются с помощью `order.id` и `correlation.id`.

---

# 19. Безопасность

Tracing-система должна находиться внутри private network.

Прямой доступ из Internet запрещён.

## Аутентификация

Доступ только сотрудникам компании.

Использовать:

- корпоративную учётную запись;
- SSO/IAM;
- MFA.

---

## Авторизация

Применяется RBAC.

Например:

```text
Support
→ read traces

Developer
→ read traces

Team Lead / SRE
→ read + manage dashboards

Administrator
→ configuration
```

---

## Network security

```text
Applications
    ↓ TLS
OpenTelemetry Collector
    ↓ TLS
Data Prepper
    ↓ TLS
OpenSearch
```

Security Groups разрешают соединения только между необходимыми компонентами.

---

## Sensitive information

В traces запрещается записывать:

- authentication tokens;
- passwords;
- payment data;
- customer personal data;
- 3D-model contents.

Collector должен дополнительно применять filtering/redaction processor.

---

## Audit

Необходимо логировать:

- вход в OpenSearch Dashboards;
- изменение tracing configuration;
- изменение access rights;
- административные операции.

---

# 20. Приоритет внедрения

Первый этап:

```text
Partner API
MES
RabbitMQ
CRM
```

Причина — именно здесь наиболее вероятна потеря B2B-заказов.

Второй этап:

```text
Online Shop
Object Storage operations
external delivery integrations
```

Такой порядок даст максимальный бизнес-эффект при ограниченных ресурсах команды.
