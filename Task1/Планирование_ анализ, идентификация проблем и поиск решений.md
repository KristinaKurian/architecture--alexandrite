# Планирование: анализ, идентификация проблем и поиск решений

## 1. Общий анализ ситуации

Архитектура компании «Александрит» формировалась постепенно.
Изначально нагрузка была небольшой, поэтому отдельные приложения онлайн-магазина, CRM и MES могли работать на одном экземпляре каждое, а базы данных — обслуживать одновременно чтение и запись.

После развития собственного производства и особенно после открытия API для внешних партнёров характер нагрузки существенно изменился:

- увеличилось количество заказов;
- появились внешние B2B-клиенты;
- длительный расчёт стоимости изделия в MES стал выполняться значительно чаще;
- вырос объём обмена сообщениями между MES и CRM;
- увеличился объём данных в MES;
- возросла нагрузка на dashboard операторов;
- существующие механизмы обработки ошибок и мониторинга перестали соответствовать масштабу системы.

Главная проблема заключается не в производственных мощностях компании.
По условию производство способно выдержать двукратный рост нагрузки.
Проблема находится в IT-контуре между созданием заказа и передачей его в производство.

Поэтому основной целью архитектурных изменений является обеспечение гарантированной обработки каждого заказа и возможность масштабирования системы без потери заказов и существенного ухудшения времени ответа.

---

# 2. Идентифицированные проблемы

## 2.1. Возможная потеря заказов при взаимодействии MES и CRM

Одна из наиболее критичных проблем — клиенты и B2B-партнёры сообщают, что не получили заказ, несмотря на его отправку.

В B2B-сценарии заказ создаётся в CRM после получения сообщения от MES через RabbitMQ. Это означает, что успешность бизнес-процесса зависит от корректной доставки и обработки сообщения.

В текущем описании отсутствует информация о наличии:

- transactional outbox;
- publisher confirms;
- persistent messages;
- manual acknowledgements;
- retry policy;
- Dead Letter Queue;
- идемпотентной обработки сообщений;
- механизма повторной отправки сообщений;
- аудита прохождения заказа между системами.

Если, например, MES успешно изменил данные в своей БД, но не смог отправить событие в RabbitMQ, состояние систем расходится.

Для пользователя операция могла выглядеть успешной, но CRM ничего об этом заказе не знает.

Обратная ситуация также возможна: сообщение доставляется несколько раз, а consumer создаёт несколько одинаковых операций.

### Последствия

- потеря заказов;
- дублирование операций;
- расхождение состояния MES и CRM;
- невозможность определить, на каком шаге потерялся заказ;
- ручное восстановление данных;

В результате финансовые и репутационные потери.

### Критичность

**Critical**

## 2.2. Длительный расчёт стоимости выполняется в контуре пользовательского API

Расчёт стоимости изделия занимает:

- обычно 2–3 минуты;
- для сложных моделей — до 30 минут.

При увеличении количества пользователей длительные операции удерживают:
- HTTP connections;
- application threads;
- connections к БД;
- память;
- CPU.

После открытия API внешним пользователям количество одновременно выполняемых расчётов резко увеличилось.

В результате MES одновременно должен:

1. обслуживать внешний API;
2. выполнять тяжёлые расчёты стоимости;
3. работать с заказами;
4. обслуживать операторский dashboard;
5. взаимодействовать с CRM.

Это создаёт конкуренцию за ресурсы одного экземпляра MES.

### Последствия

- timeout внешних API-запросов;
- исчерпание thread pool;
- рост времени ответа;
- перегрузка MES;
- снижение производительности операторского интерфейса;
- невозможность эффективно масштабировать тяжёлые вычисления отдельно от остального MES.

### Критичность

**Critical**

---

## 2.3. Внешний B2B API слишком тесно связан с MES

После открытия API MES фактически стал одновременно:

- внутренней производственной системой;
- отвечает за подсчет моделей;
- API для внешних партнёров.

Это плохая граница ответственности.

Рост трафика B2B-клиентов начинает напрямую влиять на внутренних операторов производства.

Для внешнего API также необходимы механизмы управления нагрузкой:

- rate limiting;
- quotas;
- timeout policy;
- request validation;
- throttling;
- backpressure.

Без них один крупный клиент или резкий всплеск запросов способен перегрузить MES.

### Критичность

**Critical**

---

## 2.4. Отсутствует backpressure

Скорость поступления заказов может быть выше скорости расчёта стоимости.

Система должна уметь принять такую ситуацию:

```text
1000 входящих заказов
        ↓
очередь заданий
        ↓
N workers
        ↓
постепенная обработка
```

Сейчас внешний запрос напрямую создаёт нагрузку на MES.

Очередь должна выполнять роль буфера между скоростью поступления заказов и скоростью их обработки.

### Критичность

**High**

---

## 2.5. MES не масштабируется горизонтально

MES работает в одном экземпляре.

Если экземпляр MES:

- перегружен;
- перезапускается;
- обновляется;
- становится недоступен,

останавливается значительная часть процесса обработки заказов.

При этом особенно важно иметь возможность независимо масштабировать тяжёлые операции расчёта стоимости.

### Критичность

**High**

---

## 2.6. Онлайн-магазин и CRM также имеют по одному экземпляру

Аналогичная проблема присутствует у остальных приложений.

Каждое приложение имеет один instance, поэтому отказ одного узла приводит к недоступности приложения.

При дальнейшем росте нагрузки одного instance может также оказаться недостаточно.

### Критичность

**High**

---

## 2.7. База данных одновременно обслуживает чтение и запись

Для каждой системы используется один экземпляр БД для чтения и записи.

Наиболее заметна эта проблема в MES.

Одновременно происходят:

- запись новых заказов;
- изменение статусов;
- выполнение расчётов;
- чтение операторского dashboard;
- сортировка заказов;
- фильтрация;
- пагинация.

Dashboard конкурирует с transactional workload.

### Критичность

**High**

---

## 2.8. Проблема dashboard не решается одной пагинацией

Команда уже добавила:

- фильтрацию по status;
- pagination.

Но dashboard остался медленным.

Скорее всего база вначале обрабатывает большое количество строк, выполняет сортировку и только после этого возращает нужное количество результатов.

Необходимо проверить execution plan и создать индекс, соответствующий основному запросу

При дальнейшем росте можно выделить отдельную read model для dashboard.

### Критичность

**High**

---

## 2.9. Нет единой трассировки заказа

Сейчас один заказ проходит через несколько систем. Но нет ответа на вопрос

> Где сейчас находится order `12345` и какие события с ним происходили?

Для этого нужен единый:

```text
order_id
correlation_id
event_id
```

который должен присутствовать:

- в HTTP-запросах;
- логах;
- сообщениях RabbitMQ;
- событиях;
- трассировке.

Сейчас проблема обнаруживается не мониторингом, а после жалобы клиента.

### Критичность

**Critical**

---

## 2.10. Недостаточная наблюдаемость системы

Для системы необходимо собирать не только технические, но и бизнес-метрики.

Минимальный набор:

```text
API request rate
API error rate
API latency p95/p99

RabbitMQ queue depth
age of oldest message
DLQ size

price calculation duration
active calculation workers

orders created
orders processed
orders failed

orders by status
time spent in each status

orders without transition > N minutes/hours

MES CPU / RAM
DB CPU / connections
slow queries
```

Особенно важна бизнес-метрика:

```text
возраст самого старого заказа в каждом статусе
```

Например:

```text
MANUFACTURING_APPROVED > 1 hour
```

может означать, что заказ не попал в работу.

### Критичность

**Medium**

---

## 2.11. Нет формального механизма идемпотентности

Distributed systems используют модель доставки сообщений, при которой дублирование сообщения возможно.

Поэтому нельзя рассчитывать:

```text
одно сообщение = ровно одна обработка
```

Каждое событие должно иметь уникальный `event_id`, а consumer должен безопасно обрабатывать повторную доставку.

### Критичность

**High / P0.**

---

## 2.12. Не формализована модель переходов статусов

Статус заказа меняется в нескольких системах:

- Online Shop;
- MES;
- CRM.

При распределённой архитектуре необходимо определить допустимые переходы.

Нужны:

- правила переходов;
- владельцы каждого статуса;
- история изменений;
- timestamp;
- actor/source;
- version события.

### Критичность

**High**

---

## 2.13. Недостаточная отказоустойчивость инфраструктуры

Текущая схема содержит несколько потенциальных Single Points of Failure:

```text
1 MES instance
1 CRM instance
1 Online Shop instance
1 DB writer/reader instance
```

Также необходимо проверить конфигурацию RabbitMQ:

- кластеризацию;
- quorum queues;
- persistent messages;
- replication.

Отказ одного экземпляра приложения не должен останавливать бизнес.

### Критичность

**High**

---

## 2.14. Проблемы процесса поставки изменений

QA выполняет E2E тестирование вручную.

По мере роста системы увеличивается:

- количество сценариев;
- количество интеграций;
- количество регрессий.

Из-за этого release cycle уже растягивается на недели.

Это замедляет исправление production-проблем.

Необходимо постепенно автоматизировать:

- API tests;
- integration tests;
- contract tests;
- critical E2E scenarios;
- smoke tests после deployment.


### Критичность

**Medium**

# 3. Предлагаемые инициативы

## Приоритет 1. Обеспечить гарантированную обработку заказов

Необходимо добавить надёжный messaging pattern для взаимодействия систем.

### Transactional Outbox

Изменение заказа и создание события должны происходить в одной DB transaction:

```text
BEGIN

UPDATE order ...

INSERT INTO outbox ...

COMMIT
```

Отдельный publisher читает `outbox` и отправляет события в RabbitMQ.

Таким образом исчезает проблема:

```text
данные записали
+
сообщение потеряли
```

### RabbitMQ

Необходимо использовать:

- durable queues;
- persistent messages;
- publisher confirms;
- manual acknowledgements;
- retry;
- exponential backoff;
- Dead Letter Queue.

### Consumer

Consumer должен быть идемпотентным.

Необходимо хранить обработанные `event_id`.

### Replay

Для сообщений из DLQ должен существовать контролируемый механизм повторной обработки.

### Результат

Ни один заказ не должен исчезать без возможности определить причину и повторить обработку.

---

# Приоритет 2. Сделать расчёт стоимости асинхронным

Расчёт длительностью до 30 минут нельзя выполнять как обычный синхронный HTTP request.

Предлагается перейти к модели:

```text
Client
   |
POST /orders
   |
   v
API
   |
   | 202 Accepted
   | order_id
   v
Queue
   |
   v
Pricing workers
   |
   v
MES calculation
   |
   v
PriceCalculated event
```

API должен быстро вернуть:

```http
HTTP 202 Accepted
```

например:

```json
{
  "order_id": "12345",
  "status": "PRICE_CALCULATION_PENDING"
}
```

После этого клиент может:

- получить состояние через `GET /orders/{id}`;
- использовать webhook;
- для внутреннего интерфейса — polling/SSE при необходимости.

Количество calculation workers можно масштабировать независимо.

---

# Приоритет 3. Выделить внешний Partner API из MES

Не следует предоставлять внешним компаниям прямой доступ к core MES API.

Предлагается:

```text
Partners
    |
    v
API Gateway
    |
    v
Partner / Order API
    |
    v
RabbitMQ
    |
    v
MES workers
```

API Gateway должен обеспечивать:

- rate limiting;
- quotas;
- request limits;
- timeout control;
- logging;
- metrics.

Это позволит изолировать внешний traffic от внутреннего MES.

---

# Приоритет 4. Оптимизировать операторский dashboard MES

Первый шаг — проанализировать slow query и execution plan.

Далее:

1. создать composite index по полям фильтрации и сортировки;
2. использовать keyset pagination;
3. всегда сортировать новые заказы первыми;
4. исключить N+1 queries;
5. проверить connection pool;
6. добавить query metrics.

При дальнейшем росте выделить read model.

Например:

```text
Order events
      |
      v
Dashboard projection
      |
      v
Read DB / Cache
      |
      v
MES Dashboard
```

Dashboard перестаёт выполнять тяжёлые запросы по основной transactional DB.

---

# Приоритет 5. Добавить end-to-end observability

Необходимо внедрить:

- structured logging;
- metrics;
- distributed tracing;
- correlation IDs;
- dashboards;
- alerting.

Для tracing можно использовать OpenTelemetry.

Каждый заказ должен иметь сквозной correlation ID:

```text
Partner
  ↓
API
  ↓
MES
  ↓
RabbitMQ
  ↓
CRM
```

По одному идентификатору инженер должен иметь возможность восстановить всю историю прохождения заказа.

---

# Приоритет 6. Масштабировать приложения горизонтально

Вместо:

```text
Client
  ↓
MES instance
```

должно быть:

```text
             ┌─ MES instance 1
Client → LB ─┼─ MES instance 2
             └─ MES instance 3
```

То же постепенно необходимо сделать для:

- Online Shop backend;
- CRM backend.

Приложения должны быть stateless либо хранить необходимое shared state во внешнем хранилище.

---

# Приоритет 7. Повысить отказоустойчивость БД

Для Managed DB необходимо использовать HA-конфигурацию.

Для read-heavy workload можно добавить read replica.

Логически:

```text
                 ┌→ Primary
Application ─────┤
                 └→ Read Replica
```

Transactional operations работают с primary.

Dashboard/read-only queries могут использовать replica.

---

# Приоритет 8. Защитить RabbitMQ

Необходимо проверить и при необходимости внедрить:

- RabbitMQ cluster;
- quorum queues;
- persistent messages;
- replication;
- monitoring;
- DLQ;
- backups/configuration management.

---

# Приоритет 9. Автоматизировать тестирование

QA уже заинтересован в автоматизации, поэтому это можно использовать как естественное развитие процесса.

В первую очередь автоматизировать критический путь:

```text
create order
→ upload model
→ submit
→ calculate price
→ approve
→ manufacturing
→ ship
→ close
```

Также необходимо добавить contract testing между:

- MES и CRM;
- Partner API и MES;
- producer и consumer RabbitMQ events.

---

# Приоритет 10. Улучшить CI/CD

После появления достаточного автоматического покрытия можно уменьшить стоимость релиза.

Для production желательно предусмотреть быстрый rollback и в дальнейшем canary/blue-green deployment.

---

# 4. Приоритизация инициатив

Инициативы предлагается реализовывать в следующем порядке:

| Приоритет | Инициатива | Причина |
|---|---|---|
| P0 | Надёжная доставка заказов: Outbox + idempotency + retry + DLQ | Компания уже теряет заказы и клиентов |
| P0 | Асинхронный расчёт стоимости | Операция занимает до 30 минут и перегружает MES |
| P0 | Partner API + rate limiting + backpressure | Внешние клиенты создают неконтролируемую нагрузку |
| P0 | Observability и сквозная трассировка заказов | Сейчас проблемы обнаруживаются по жалобам пользователей |
| P0/P1 | Оптимизация MES dashboard | Операторы не могут своевременно получать новые заказы |
| P1 | Горизонтальное масштабирование MES | Один instance является bottleneck и SPOF |
| P1 | HA и read replica для DB | Разделение transactional и read workload |
| P1 | Повышение отказоустойчивости RabbitMQ | Messaging становится критической частью системы |
| P1 | Автоматизация тестирования | Уменьшение regression и времени release |
| P2 | Улучшение CI/CD | Ускорение и повышение безопасности delivery |

---

# 5. Целевая архитектура через полгода

Я не считаю целесообразным за полгода полностью переписывать существующие CRM и MES или искусственно разбивать их на большое количество микросервисов.

Это создаст слишком большой migration risk для небольшой команды.

Оптимальным будет эволюционное изменение архитектуры.

Целевая схема:

```text
                          B2C clients
                              |
                              v
                     Online Shop
                              |
                              |
B2B Partners                 |
     |                       |
     v                       |
 API Gateway                 |
     |                       |
     v                       |
 Partner / Order API <-------+
     |
     | 202 Accepted
     |
     v
 RabbitMQ / Job Queue
     |
     +-----------------------+
     |                       |
     v                       v
Pricing Worker          Pricing Worker
     |                       |
     +-----------+-----------+
                 |
                 v
                MES
                 |
        Transactional Outbox
                 |
                 v
              RabbitMQ
                 |
                 v
                CRM


MES/CRM events
      |
      v
Order / Dashboard Projection
      |
      v
Read Model / Cache
      |
      v
MES Dashboard
```

Дополнительно:

```text
Applications
      |
Load Balancer
      |
+-----+-----+
|     |     |
App1 App2 App3
```

и:

```text
Database
 |
 +---- Primary
 |
 +---- Read Replica
```

---

## Основные характеристики целевой архитектуры

### 1. Надёжность

Каждый заказ имеет:

```text
order_id
event_id
correlation_id
```

Все изменения состояния можно проследить.

События не теряются за счёт:

- transactional outbox;
- retry;
- DLQ;
- idempotent consumers.

---

### 2. Асинхронность

Долгий расчёт стоимости выполняется вне HTTP request.

HTTP API только принимает команду и возвращает идентификатор задания.

---

### 3. Масштабируемость

Calculation workers можно масштабировать отдельно от MES.

MES, CRM и Online Shop могут иметь несколько application instances.

---

### 4. Изоляция B2B-нагрузки

External API больше не создаёт прямую неконтролируемую нагрузку на MES.

---

### 5. Быстрый dashboard

Операторский интерфейс использует оптимизированный read path.

Новые заказы отображаются первыми.

---

### 6. Наблюдаемость

Проблема определяется автоматически по monitoring/alerting, а не после обращения клиента.

# 7. Если можно выполнить только три инициативы

Если в ближайшие полгода можно реализовать только три крупные инициативы, я выберу следующие.

## 1. Гарантированная доставка и обработка заказов

Сюда входят:

- transactional outbox;
- idempotency;
- retry;
- DLQ;
- correlation ID;
- аудит движения заказа.

### Почему это №1

Компания уже теряет реальные заказы и контракты.

Главный критерий:

> Каждый принятый заказ должен либо успешно обработаться, либо оказаться в контролируемом состоянии ошибки, из которого его можно восстановить.

---

## 2. Асинхронный расчёт стоимости и изоляция Partner API

Расчёт занимает до 30 минут, поэтому его необходимо вынести из synchronous request path.

Необходимо:

```text
Partner
   ↓
API Gateway
   ↓
Order API
   ↓
Queue
   ↓
Scalable Pricing Workers
   ↓
MES
```

### Почему это №2

Именно открытие B2B API резко увеличило проблемы.

Эта инициатива:

- защищает MES от всплесков нагрузки;
- позволяет масштабировать расчёты независимо;
- вводит backpressure;
- устраняет длинные HTTP requests;
- позволяет применять rate limiting;
- позволяет выдерживать дальнейший рост количества заказов.

---

## 3. Разгрузка и масштабирование MES

Эта инициатива включает:

- оптимизацию dashboard queries;
- composite indexes;
- keyset pagination;
- read model/read replica для dashboard;
- несколько экземпляров MES за load balancer;
- масштабирование тяжёлых workers отдельно.

### Почему это №3

Даже если заказ надёжно попал в систему, он должен своевременно попасть к оператору.

Сейчас операторы не могут быстро увидеть новые заказы, а это непосредственно влияет на скорость запуска производства.

Кроме того, один instance MES остаётся как performance bottleneck, так и Single Point of Failure.

---

# 8. Почему я не предлагаю сразу переписать всю систему

Полный переход CRM и MES на микросервисы за шесть месяцев считаю неоправданным.

Причины:

- небольшая инженерная команда;
- только один основной C# developer для MES;
- MES содержит критичную бизнес-логику расчёта;
- бизнес уже находится в кризисной ситуации;
- rewrite создаст дополнительные риски и замедлит устранение текущих проблем.

Предпочтителен подход постепенной модернизации:

```text
стабилизировать
      ↓
сделать observable
      ↓
обеспечить delivery guarantees
      ↓
вынести тяжёлые операции
      ↓
масштабировать
      ↓
постепенно менять границы системы
```

Это позволяет получать бизнес-эффект после каждого этапа, а не ждать завершения большого rewrite.

---

# 9. Изменения в команде

Большую часть первоначальных изменений можно начать существующей командой.

Распределение ответственности:

- Java backend engineers — Partner/Order API, integration components;
- C# developer и team lead — изменения MES и pricing integration;
- DevOps — RabbitMQ, observability, load balancing, autoscaling, CI/CD;
- QA — автоматизация critical E2E и API scenarios;
- frontend developers — изменения B2B/B2C UX для asynchronous status.

При дальнейшем росте полезно нанять ещё одного backend engineer с опытом distributed systems/messaging. Это снизит bus factor и ускорит работу с интеграциями.

При существенном росте инфраструктуры также может понадобиться второй DevOps/SRE engineer, так как один специалист станет bottleneck для эксплуатации production-системы.

---

# 10. Ожидаемый результат

После выполнения плана система должна перейти от архитектуры, в которой проблемы обнаруживаются после жалоб клиентов, к архитектуре, где:

- каждый заказ прослеживается от создания до закрытия;
- сообщения можно безопасно повторно обработать;
- потерянные сообщения попадают в DLQ;
- долгий расчёт стоимости выполняется асинхронно;
- внешний API не может перегрузить MES;
- расчётные workers масштабируются независимо;
- оператор быстро видит новые заказы;
- приложения не зависят от одного instance;
- система имеет мониторинг и alerting;
- релизы проходят быстрее благодаря автоматизации тестирования.

Таким образом, основной фокус первых шести месяцев — не полный redesign системы, а устранение причин потери заказов и создание архитектурной основы, которая позволит «Александриту» продолжать рост без пропорционального роста количества инцидентов.
