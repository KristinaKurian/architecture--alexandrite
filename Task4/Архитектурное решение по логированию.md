# Архитектурное решение по логированию

## 1. Анализ системы

Сейчас расследование проблемы начинается со слов клиента.

Например:

> «Я создал заказ, но он так и не появился в производстве».

После этого разработчикам приходится вручную проверять несколько систем.

Централизованного механизма, позволяющего найти события конкретного заказа, нет.

Цель решения — создать единое централизованное хранилище structured logs и связать логи с tracing через:

```text
trace_id
span_id
correlation_id
order_id
event_id
```

# 3. Формат логов

Все application logs должны быть structured.

Предлагается JSON.

Пример:

```json
{
  "timestamp": "2026-09-11T10:15:32Z",
  "level": "INFO",
  "service": "mes",
  "environment": "prod",
  "version": "2.14.1",

  "trace_id": "4bf92f...",
  "span_id": "00f067...",
  "correlation_id": "corr-123",
  "order_id": "12345",
  "event_id": "evt-456",

  "operation": "price_calculation_completed",
  "order_status_from": "SUBMITTED",
  "order_status_to": "PRICE_CALCULATED",

  "duration_ms": 175240,
  "result": "success"
}
```

Преимущество structured logs в том, что можно выполнять запросы:

```text
order_id = 12345
```

или:

```text
trace_id = ...
```

без разбора произвольного текста.

# 5. Другие уровни логирования

## DEBUG

Используется для подробной технической диагностики.

Например:

```text
SQL execution details
internal calculation stages
serialization details
RabbitMQ client diagnostics
```

В production по умолчанию отключён.

Включается временно для конкретного сервиса.

---

## INFO

Нормальный бизнес-процесс.

Например:

```text
order created
price calculated
message published
status changed
```

---

## WARN

Проблема произошла, но система смогла продолжить работу.

Например:

```text
retry #2
slow request
slow query
queue backlog increasing
rate limit applied
external API temporary failure
```

---

## ERROR

Операция не выполнена.

Например:

```text
price calculation failed
database operation failed
message processing failed
HTTP 500
```

Для ERROR необходимо сохранять:

```text
error.type
error.code
stacktrace
```

Stacktrace не должен содержать credentials или персональные данные.

---

## CRITICAL/FATAL

Используется только для событий, из-за которых приложение не может продолжить работу.

Например:

```text
cannot start application
database permanently unavailable
configuration invalid
```

---

# 6. Что запрещено писать в logs

В логах нельзя хранить:

- пароль;
- access token;
- refresh token;
- Authorization header;
- cookies;
- номер банковской карты;
- CVV;
- полные персональные данные;
- содержимое 3D-модели;
- бинарные данные;
- connection strings с паролями.

Необходимо применять masking.

Например:

```text
email:
k***@example.com

phone:
+374******42
```

Если customer identity не нужна для расследования — её вообще не следует логировать.

# 7. Мотивация

Централизованное логирование позволит перейти от ручного поиска проблем к расследованию по конкретным идентификаторам.

Например, support получает:

```text
order_id=12345
```

и выполняет один запрос.

Результат:

```text
10:01 Shop    order SUBMITTED
10:01 MES     order received
10:04 MES     PRICE_CALCULATED
10:04 MES     event published
10:04 CRM     event received
10:04 CRM     ERROR database timeout
```

Причина становится понятна за минуты.

# 8. Показатели, на которые повлияет logging

## MTTR

Сократится среднее время устранения incident.

---

## Среднее время обработки обращения поддержки

Support сможет быстрее определить техническую причину.

---

## Количество обращений, требующих участия разработчика

Часть проблем support сможет диагностировать самостоятельно.

---

## Процент заказов с восстанавливаемой историей

Для каждого заказа должна существовать последовательность ключевых business logs.

---

## Количество повторяющихся production incidents

Search и aggregation позволят находить системные ошибки, а не исправлять каждый заказ отдельно.

# 9. Приоритет внедрения tracing и logging

Команда не может инструментировать всё одновременно.

Первый приоритет:

```text
Partner API
   ↓
MES
   ↓
RabbitMQ
   ↓
CRM
```

Причины:

- именно после открытия Partner API резко выросло количество проблем;
- здесь создаются B2B-заказы;
- присутствует длительный calculation;
- используется asynchronous messaging;
- возможна потеря сообщений;
- компания уже потеряла контракты.

Второй приоритет:

```text
Online Shop
Object Storage
Delivery integration
```

# 12. Корреляция logs и traces

Каждый application log должен автоматически содержать:

```text
trace_id
span_id
```

Для business events дополнительно:

```text
correlation_id
order_id
event_id
```

В результате из trace можно перейти к logs конкретного span.

И наоборот:

```text
ERROR log
 ↓
trace_id
 ↓
полный distributed trace
```

# 13. OpenSearch

В качестве центрального log storage предлагается использовать:

```text
Yandex Managed Service for OpenSearch
```

Причины:

- полнотекстовый поиск;
- structured search;
- aggregations;
- dashboards;
- alerting;
- anomaly detection;
- поддержка Trace Analytics;
- managed service уже доступен в используемом облаке.

# 14. Индексы

Не следует складывать все environment и сервисы в один бесконечный индекс.

Предлагаются index patterns:

```text
logs-prod-shop-*
logs-prod-mes-*
logs-prod-crm-*
logs-prod-partner-api-*
logs-prod-rabbitmq-*

logs-release-*
logs-dev-*
```

Для security/audit logs:

```text
audit-prod-*
```

---

# 15. Rollover

Необходимо настроить Index State Management.

Новый индекс создаётся:

```text
раз в сутки

ИЛИ

при достижении примерно 20 GB
```

в зависимости от того, что произойдёт раньше.

Это не позволяет одному индексу вырасти до неконтролируемого размера.

После накопления production statistics значение необходимо уточнить.

---

# 16. Retention

Предлагаемая первоначальная политика:

| Тип | Retention |
|---|---:|
| DEV logs | 7 дней |
| RELEASE logs | 14 дней |
| PROD application logs | 30 дней |
| PROD ERROR/security/audit logs | 90 дней |
| Audit доступа | до 180 дней при необходимости |

30 дней production logs позволяют расследовать проблемы заказов, жизненный цикл которых измеряется неделями.

После анализа реального объёма retention необходимо скорректировать.

---

# 17. Размер хранилища

Точный объём нельзя выбрать без измерения реального log rate.

Необходимо сначала измерить:

```text
average event size
×
events per second
×
86400
×
retention days
```

Например:

```text
daily_log_volume =
average_log_size × logs_per_second × 86400
```

Далее добавить:

```text
replication factor
+
20–30% reserve
```

Не следует заранее выделять произвольные терабайты без измерений.

# 18. Безопасность

## Network

OpenSearch и Data Prepper находятся в private network.

OpenSearch Dashboards не должен быть напрямую доступен из Internet.

---

## Authentication

Использовать:

- корпоративную учётную запись;
- IAM/SSO;
- MFA.

---

## RBAC

### Support

Доступ:

```text
read production application logs
```

без административных функций.

### Developer

```text
read logs
create saved queries
```

### SRE / Team Lead

```text
read logs
manage dashboards
manage alerts
```

### Administrator

```text
cluster configuration
access control
index management
```

---

## Service accounts

Collector/Data Prepper получает отдельный service account с минимальными правами:

```text
write logs
```

Но не:

```text
manage users
delete arbitrary data
change security settings
```

---

## Encryption

Использовать TLS:

```text
Application
    ↓ TLS
Collector
    ↓ TLS
Data Prepper
    ↓ TLS
OpenSearch
```

# 21. Alerting

Необходимо настроить alert на:

```text
ERROR logs резко выросли
```

например:

```text
ERROR > normal threshold
за 5 минут
```

---

Также:

```text
price_calculation_failed
```

превышает допустимую частоту.

---

Также:

```text
message_processing_failed
```

или:

```text
retry.count > threshold
```

---

Для security:

```text
много HTTP 401/403
```

может означать попытку атаки.

---

# 22. Поиск аномалий

Не все проблемы удобно задавать статическим threshold.

Например, обычно система создаёт:

```text
100 заказов / час
```

и неожиданно начинает получать:

```text
10 000 заказов / минуту
```

Это может означать:

- ошибку клиента;
- runaway integration;
- bot activity;
- DDoS;
- злоупотребление API.

Для таких случаев предлагается использовать OpenSearch Anomaly Detection.

Анализировать:

```text
orders_created
HTTP requests
ERROR logs
authentication failures
RabbitMQ retries
price calculation failures
```

# 27. Почему выбран OpenSearch

Для «Александрита» OpenSearch является наиболее сбалансированным вариантом.

Главные причины:

1. Есть Yandex Managed Service for OpenSearch.
2. Не требуется самостоятельно администрировать весь cluster.
3. Apache 2.0.
4. Хороший full-text search.
5. Поддерживает structured log analytics.
6. Есть dashboards.
7. Есть alerting.
8. Есть anomaly detection.
9. Можно использовать тот же backend для tracing.
10. Хорошо интегрируется с OpenTelemetry/Data Prepper.

# 29. Ожидаемый результат

После реализации команда должна иметь возможность взять:

```text
order_id
```

и за несколько минут восстановить путь заказа:

```text
когда создан
→ где обработан
→ когда посчитана цена
→ какое событие опубликовано
→ кто получил сообщение
→ где произошла ошибка
→ сколько было retry
→ какой trace соответствует ошибке
```

Вместо расследования со слов клиента команда получает объективную техническую историю события.

Это уменьшает время расследования, снижает нагрузку на поддержку и позволяет выявлять системные проблемы до того, как они приведут к массовой потере заказов.
