# Выбор и настройка мониторинга в системе

## 1. Мотивация

На текущий момент основным инструментом наблюдения за поведением пользователей интернет-магазина является Яндекс Метрика.

После открытия API для внешних партнёров этого стало недостаточно. 
Яндекс Метрика позволяет анализировать действия пользователей сайта, но не позволяет получить полную картину состояния внутренних компонентов системы и B2B-интеграций.

Основные проблемы компании сейчас связаны не только с веб-интерфейсом:

- некоторые заказы не доходят до следующих этапов обработки;
- увеличилось число заказов через API;
- MES испытывает повышенную нагрузку;
- расчёт стоимости изделия занимает от 2–3 до 30 минут;
- операторы жалуются на медленную работу MES;
- взаимодействие MES и CRM зависит от RabbitMQ;
- отсутствует возможность быстро определить, на каком этапе потерялся конкретный заказ;
- проблемы обнаруживаются после обращения клиента, а не автоматически;
- неизвестно, является ли причиной проблемы приложение, база данных, очередь сообщений или инфраструктура.

Поэтому компании необходим технический и бизнес-мониторинг.

Главная задача мониторинга — перейти от реактивной модели:

```text
Клиент пожаловался
        ↓
Команда узнала о проблеме
        ↓
Начался поиск причины
```

к проактивной:

```text
Метрика вышла за допустимый диапазон
        ↓
Сработал alert
        ↓
Команда увидела компонент и причину
        ↓
Проблема исправляется до массовых жалоб
```

### Что мониторинг даст бизнесу

#### 1. Уменьшение количества потерянных заказов

Можно отслеживать:

- количество сообщений в RabbitMQ;
- сообщения в DLQ;
- возраст самого старого сообщения;
- заказы, которые слишком долго не меняют статус;
- ошибки обработки событий между MES и CRM.

Это позволит обнаруживать проблемы до обращения клиента.

---

#### 2. Снижение времени обнаружения и устранения инцидентов

Без мониторинга при жалобе:

> «Заказ отправили две недели назад, но его до сих пор нет»

команде приходится вручную проверять:

- интернет-магазин;
- MES;
- CRM;
- RabbitMQ;
- базы данных;
- application logs.

При наличии мониторинга и сквозных идентификаторов можно быстро определить:

```text
Order 12345
SUBMITTED
    ↓
PRICE_CALCULATED
    ↓
RabbitMQ
    X
CRM message processing failed
```

Это уменьшает MTTD — Mean Time To Detect — и MTTR — Mean Time To Repair.

---

#### 3. Возможность планировать мощности

Нагрузка растёт каждый месяц.

Необходимо видеть:

- рост RPS;
- CPU;
- memory;
- количество соединений к БД;
- размер очередей;
- продолжительность расчёта стоимости;
- число одновременно обрабатываемых заказов.

На основании этих данных можно заранее масштабировать систему, а не делать это после деградации production.

---

#### 4. Контроль качества B2B API

После открытия API появились внешние клиенты.

Для них необходимо контролировать:

- доступность API;
- количество запросов;
- latency;
- error rate;
- количество заказов;
- время обработки заказов.

Это позволит в дальнейшем сформировать формальные SLI/SLO и при необходимости SLA.

---

#### 5. Контроль бизнес-процесса

Технически сервер может быть доступен, CPU может быть 30%, а бизнес при этом продолжает терять заказы.

Поэтому необходимо контролировать не только инфраструктуру, но и сам жизненный цикл заказа.

Например:

```text
orders_created_total
orders_completed_total
orders_failed_total
orders_by_status
order_status_duration
price_calculation_duration
stuck_orders
```

---

# 2. Выбор подхода к мониторингу

Использовать один подход для всех компонентов системы нецелесообразно.

Для разных частей системы предлагается применять разные методологии.

## 2.1. RED — для API

Для:

- Internet Shop API;
- CRM API;
- MES API;
- будущего Partner API

будет использоваться подход **RED**:

- **Rate** — количество запросов;
- **Errors** — количество ошибочных запросов;
- **Duration** — продолжительность запросов.

Для API это наиболее важные показатели с точки зрения пользователя.


Так можно быстро определить, испытывает ли API деградацию.

---

## 2.2. USE — для инфраструктуры

Для:

- виртуальных машин;
- баз данных;
- RabbitMQ;
- application runtime;
- connection pools

будет использоваться подход **USE**:

- **Utilization** — насколько ресурс используется;
- **Saturation** — сколько запросов ожидают ресурс;
- **Errors** — ошибки ресурса.

---

## 2.3. Четыре золотых сигнала — для бизнес-процесса заказа

Для всего order pipeline полезно рассматривать четыре золотых сигнала:

### Traffic

Количество новых заказов:

```text
orders_created_total
```

### Latency

Время прохождения заказа и отдельных этапов:

```text
price_calculation_duration
order_status_duration
order_end_to_end_duration
```

### Errors

```text
orders_failed_total
DLQ messages
price_calculation_failed_total
```

### Saturation

```text
pricing_queue_depth
oldest_message_age
active_workers
orders_waiting_for_processing
```

# 3. Общие правила для метрик и labels

Для всех метрик необходимо использовать единый набор базовых labels.

Например:

```text
environment="prod"
service="mes"
instance="mes-01"
```

Для API дополнительно:

```text
method="POST"
route="/orders/{id}"
status_class="2xx"
```

Для RabbitMQ:

```text
queue="orders"
vhost="production"
```

Для business metrics:

```text
source="b2b"
status="SUBMITTED"
```

## Необходимо избегать high-cardinality labels

Не следует использовать в time-series metrics:

```text
order_id
user_id
request_id
correlation_id
file_name
raw_url
```

# 4. Метрики API

## 4.1. Number of requests — RPS

Отслеживать для:

- Internet Shop API;
- CRM API;
- MES API.

Метрики из предложенного списка:

- №3 — RPS Internet Shop API;
- №4 — RPS CRM API;
- №5 — RPS MES API.

Пример:

```text
http_requests_total
```

Labels:

```text
service
environment
method
route
status_class
```

Например:

```text
http_requests_total{
    service="mes",
    method="POST",
    route="/orders",
    status_class="2xx"
}
```

### Зачем

RPS показывает реальную нагрузку на приложение.

Можно:

- определить часы пик;
- найти резкие всплески;
- сравнивать B2C и B2B traffic;
- планировать масштабирование;
- увидеть эффект подключения нового партнёра.

---

# 4.2. RPS per user

Метрики №6–8 **не предлагается хранить напрямую как Prometheus metrics с `user_id` label**.

Причина — высокая cardinality.

Если пользователей тысячи или миллионы:

```text
user_id=1
user_id=2
...
user_id=1000000
```

будет создано огромное число временных рядов.

Для B2B API информация по конкретному партнёру всё же важна для rate limiting.

Но её лучше собирать:

- на API Gateway;
- в access logs;
- в отдельной аналитике;
- в rate limiter.

Если количество партнёров строго ограничено, допустима агрегированная метрика:

```text
source="b2b"
partner_tier="gold"
```

но не произвольный `user_id`.

---

# 4.3. API latency

Выбираются метрики:

- №19 — Shop API latency;
- №20 — CRM API latency;
- №21 — MES API latency.

Метрика:

```text
http_request_duration_seconds
```

Labels:

```text
service
environment
method
route
```

Необходимо анализировать не только average, но и percentiles:

```text
p50
p95
p99
```

Среднее значение может скрыть проблему.

Например:

```text
average = 200 ms
p95     = 800 ms
p99     = 8 sec
```

Для 1% пользователей система фактически работает плохо, хотя average выглядит нормально.

Особенно важно отдельно отслеживать:

```text
MES dashboard
order submit
price calculation submit
order status
```

---

# 4.4. HTTP response codes

Выбираются:

- №25–27 — HTTP 200;
- №28–30 — HTTP 500.

Но лучше не создавать отдельную метрику на каждый код.

Используется одна:

```text
http_requests_total
```

с label:

```text
status_code
```

или:

```text
status_class
```

Например:

```text
status_class="2xx"
status_class="4xx"
status_class="5xx"
```

### Зачем

Позволяет вычислять error rate:

```text
5xx requests / all requests
```

и сравнивать его между сервисами и endpoint.

Также важно различать:

- 4xx — клиентские ошибки;
- 5xx — серверные ошибки.

---

# 4.5. Одновременные запросы

Метрики №32–34 предлагается интерпретировать не как пользовательские HTTP sessions, а как:

```text
http_requests_active
```

для каждого приложения.

Labels:

```text
service
environment
instance
```

### Зачем

Большое количество одновременно выполняемых запросов может показывать:

- зависшие запросы;
- медленные downstream services;
- исчерпание thread pool;
- недостаточное количество instances.

Особенно это актуально для текущего MES, где расчёт стоимости может занимать десятки минут.

---

# 5. Метрики application instances

Выбираются:

- №9–11 — CPU;
- №12–14 — Memory Utilisation.

Метрики:

```text
cpu_usage_percent
memory_usage_percent
```

Labels:

```text
service
environment
instance
```

### Зачем CPU

Позволяет увидеть:

- перегрузку приложения;
- влияние тяжёлых 3D-расчётов;
- необходимость horizontal scaling;
- abnormal CPU consumption.

Для MES это одна из основных saturation metrics.

### Зачем Memory

Позволяет выявлять:

- memory leak;
- недостаточный размер instance;
- Out Of Memory;
- влияние одновременной обработки больших 3D-моделей.

Дополнительно необходимо отслеживать:

```text
process_cpu
process_memory
GC pause
thread pool usage
```

для Spring Boot и .NET runtime.

---

# 6. Метрики RabbitMQ

RabbitMQ — критически важный компонент, поскольку через него интегрируются MES и CRM.

## 6.1. DLQ messages

Выбирается метрика №1:

```text
rabbitmq_dlq_messages
```

или фактическое количество сообщений в соответствующей DLQ.

Labels:

```text
environment
vhost
queue
```

### Зачем

В нормальной ситуации DLQ для событий заказов должна быть пустой.

Если:

```text
DLQ > 0
```

значит событие невозможно обработать после retry.

Для бизнес-критичного order flow это потенциально потерянный заказ.

Поэтому метрика является критичной.

---

# 6.2. Messages in flight

Выбирается метрика №2.

Например:

```text
rabbitmq_messages_unacked
```

Labels:

```text
environment
vhost
queue
```

### Зачем

Большое число `unacked` сообщений может означать:

- consumer работает медленно;
- consumer завис;
- downstream DB тормозит;
- обработка события слишком тяжёлая.

---

# 6.3. Queue depth

Дополнительная метрика:

```text
rabbitmq_queue_messages_ready
```

### Зачем

Показывает backlog.

Если:

```text
messages arriving > messages processing
```

очередь будет постоянно расти.

Это прямой индикатор отсутствия достаточной processing capacity.

---

# 6.4. Age of oldest message

Дополнительная и очень важная метрика:

```text
rabbitmq_oldest_message_age_seconds
```

Она зачастую полезнее, чем просто queue length.

Пример:

```text
Queue A = 10 000 messages
oldest = 5 sec
```

может быть нормой для производительной системы.

Но:

```text
Queue B = 20 messages
oldest = 30 min
```

может означать серьёзную проблему.

Особенно эта метрика важна для заказов.

---

# 6.5. Message rates

Необходимо собирать:

```text
messages_published_rate
messages_delivered_rate
messages_acked_rate
messages_redelivered_rate
```

Labels:

```text
queue
vhost
environment
```

### Зачем

Позволяет определить:

```text
published > acknowledged
```

и заранее увидеть накопление backlog.

Большой `redelivered_rate` может свидетельствовать об ошибках consumer.

---

# 6.6. Consumers

Метрика:

```text
rabbitmq_consumers
```

Если для критической очереди:

```text
consumers = 0
```

должен срабатывать alert.

---

# 7. Метрики баз данных

Из списка выбираются:

- №15 — Memory Utilisation Shop DB;
- №16 — Memory Utilisation MES DB;
- №17 — Number of connections Shop DB;
- №18 — Number of connections MES DB;
- №23 — Size Shop DB;
- №24 — Size MES DB.

Дополнительно необходимы:

```text
DB CPU
disk utilisation
disk IO
query latency
active connections
waiting connections
slow queries
lock waits
```

Если появятся replicas:

```text
replication lag
```

---

## 7.1. DB connections

Очень важная saturation metric.

Необходимо рассчитывать:

```text
current_connections / max_connections
```

Labels:

```text
database
environment
host
role
```

### Зачем

Если connection pool практически исчерпан:

```text
95 / 100 connections
```

новые запросы начинают ждать свободного соединения или завершаться ошибкой.

Внешне это будет выглядеть как «MES тормозит».

---

## 7.2. Query latency

Дополнительная метрика.

Особенно необходимо отслеживать запрос dashboard MES.

Например:

```text
db_query_duration_seconds
```

или агрегированные значения:

```text
p50
p95
p99
```

Не следует помещать полный SQL query в label.

Можно использовать:

```text
query_name="mes_dashboard_orders"
```

---

## 7.3. DB size и disk utilisation

Размер БД сам по себе не означает проблему, но важен для capacity planning.

Необходимо контролировать:

```text
db_size_bytes
disk_usage_percent
disk_free_bytes
```

---

# 8. Метрики S3/Object Storage

Из предложенного списка выбирается №22:

```text
S3 storage size
```

Дополнительно:

```text
number_of_objects
upload_errors
download_errors
```

### Зачем

В Object Storage могут находиться большие 3D-модели изделий.

Рост количества заказов означает рост storage.

Метрика используется для:

- capacity planning;
- cost monitoring;
- поиска аномального роста данных.

Labels:

```text
bucket
environment
```

Не нужно использовать object key как label.

---

# 9. Network metrics

Метрики №35–40:

- received bytes;
- sent bytes.

Их имеет смысл собирать на infrastructure level.

Например:

```text
network_receive_bytes
network_transmit_bytes
```

Labels:

```text
service
instance
environment
```

Но их приоритет ниже, чем:

- API latency;
- errors;
- queue depth;
- CPU;
- DB connections.

Они полезны для диагностики аномальных нагрузок и capacity planning.

---

# 10. Бизнес-метрики

Одних технических метрик недостаточно.

Необходимо добавить business metrics.

## 10.1. Созданные заказы

```text
orders_created_total
```

Labels:

```text
source="b2c|b2b"
environment
```

Позволяет видеть реальную бизнес-нагрузку.

---

## 10.2. Заказы по статусам

```text
orders_current
```

Labels:

```text
status
source
environment
```

Например:

```text
status="SUBMITTED"
status="PRICE_CALCULATED"
status="MANUFACTURING_APPROVED"
status="MANUFACTURING_STARTED"
status="MANUFACTURING_COMPLETED"
status="PACKAGING"
status="SHIPPED"
status="CLOSED"
```

Так можно определить место накопления заказов.

---

# 10.3. Время нахождения заказа в статусе

```text
order_status_duration_seconds
```

Labels:

```text
status
source
```

### Зачем

Например, рост времени:

```text
SUBMITTED
    ↓
PRICE_CALCULATED
```

указывает на проблему расчёта стоимости.

А рост:

```text
MANUFACTURING_APPROVED
    ↓
MANUFACTURING_STARTED
```

может говорить о том, что операторы не видят новые заказы либо MES работает слишком медленно.

---

# 10.4. Продолжительность расчёта стоимости

```text
price_calculation_duration_seconds
```

Labels:

```text
source
result="success|failed"
complexity_bucket
```

Вместо количества полигонов как произвольного label лучше использовать ограниченное число категорий, например:

```text
complexity_bucket="small"
complexity_bucket="medium"
complexity_bucket="large"
```

### Зачем

По условию обычный расчёт занимает 2–3 минуты, сложный — до 30 минут.

Метрика позволит определить:

- увеличение времени расчёта;
- влияние сложности модели;
- capacity worker pool;
- необходимые ресурсы.

---

# 10.5. Время ожидания расчёта

После перехода на асинхронную модель необходимо добавить:

```text
price_calculation_queue_wait_seconds
```

Это время:

```text
заказ попал в очередь
        ↓
worker начал расчёт
```

Важно отделять:

```text
queue wait
```

от:

```text
calculation time
```

Иначе невозможно понять, почему пользователь долго ждёт цену.

---

# 10.6. Ошибки заказов

```text
orders_failed_total
```

Labels:

```text
stage
source
error_type
```

`error_type` должен иметь небольшой фиксированный набор значений.

Нельзя помещать полный exception text в label.

---

# 10.7. Зависшие заказы

Одна из самых важных бизнес-метрик:

```text
stuck_orders_total
```

Например:

```text
SUBMITTED > 30 minutes
```

или:

```text
заказ не изменялся значительно дольше нормального времени этапа
```

Labels:

```text
status
source
```

---

# 10.8. End-to-end processing time

```text
order_end_to_end_duration_seconds
```

Например:

```text
SUBMITTED → SHIPPED
```

Бизнес обещает изготовление примерно за три недели, поэтому эта метрика непосредственно показывает качество выполнения обещаний клиентам.

Необходимо отображать:

```text
p50
p90
p95
```

и количество заказов, приближающихся к согласованному сроку.

---

# 11. Итоговый набор основных метрик

| Область | Метрика | Подход | Основные labels | Назначение |
|---|---|---|---|---|
| Shop API | RPS | RED | service, route, method, env | Нагрузка |
| CRM API | RPS | RED | service, route, method, env | Нагрузка |
| MES API | RPS | RED | service, route, method, env | Нагрузка |
| API | Latency p50/p95/p99 | RED | service, route, method, env | Деградация API |

# 12. Метрики, которые не являются приоритетными

Не все метрики из предложенного списка одинаково полезны.

Например:

```text
Number of HTTP 200
```

не нужно хранить отдельной метрикой, если уже существует:

```text
http_requests_total{status_class="2xx"}
```

А метрики:

```text
RPS per user
```

не следует реализовывать через `user_id` labels из-за высокой cardinality.

Также количество simultaneous sessions для stateless REST API менее информативно, чем:

```text
active requests
thread pool saturation
connection pool saturation
```

# 16. Показатели насыщенности

Пороговые значения необходимо рассматривать как первоначальные. После получения реальной статистики и нагрузочного тестирования они должны быть уточнены.

## 16.1. CPU

### Warning

```text
CPU > 70%
в течение 10 минут
```

### Critical

```text
CPU > 85%
в течение 10 минут
```

### Действия

Warning:

- проверить RPS;
- проверить тяжёлые операции;
- проверить latency.

Critical:

- увеличить количество application instances;
- для pricing workers — выполнить horizontal scale;
- создать incident, если autoscaling не помог.

---

# 16.2. Memory

### Warning

```text
Memory > 75%
```

### Critical

```text
Memory > 90%
```

### Действия

Проверить:

- memory leak;
- GC;
- размер 3D-моделей;
- количество parallel calculations.

При необходимости:

- restart unhealthy instance;
- увеличить memory;
- добавить instances.

---

# 16.3. DB connections

Важен не абсолютный показатель, а процент:

```text
connections / max_connections
```

### Warning

```text
> 70%
```

### Critical

```text
> 85%
```

### Действия

Проверить:

- connection leak;
- pool settings;
- slow queries;
- долгие transactions.

Не следует автоматически увеличивать `max_connections` без анализа причины.

---

# 16.4. Database disk

### Warning

```text
disk > 75%
```

### Critical

```text
disk > 85%
```

### Действия

- проверить скорость роста;
- увеличить storage;
- проверить старые данные/logs;
- проверить retention.

---

# 16.5. API error rate

### Warning

```text
5xx > 1%
за 5 минут
```

### Critical

```text
5xx > 5%
за 5 минут
```

### Действия

Warning:

- сообщение команде;
- проверить logs/traces.

Critical:

- incident;
- уведомление on-call;
- при связи с новой версией — rollback.

---

# 16.6. API latency

Первоначальные target для обычных API endpoints:

### Warning

```text
p95 > 1 second
```

### Critical

```text
p95 > 3 seconds
```

Для endpoints с иной бизнес-спецификой SLO устанавливается отдельно.

Длительный расчёт стоимости не должен измеряться как обычный HTTP request после перехода на asynchronous processing.

---

# 16.7. RabbitMQ DLQ

Для order events:

### Critical

```text
DLQ > 0
```

Даже одно сообщение требует внимания, потому что оно может соответствовать реальному заказу.

### Действия

```text
Alert
→ incident
→ определить event
→ исправить причину
→ controlled replay
```

---

# 16.8. RabbitMQ consumers

### Critical

```text
consumers = 0
```

для critical order queue более нескольких минут.

### Действия

- проверить consumer instances;
- выполнить restart/scale;
- проверить deployment;
- создать incident.

---

# 16.9. Возраст сообщения в integration queue

Для сообщений MES → CRM:

### Warning

```text
oldest message > 1 minute
```

### Critical

```text
oldest message > 5 minutes
```

Переход заказа между системами не должен занимать значительное время.

### Действия

- проверить consumers;
- DB latency;
- ошибки CRM;
- увеличить число consumers, если причиной является нагрузка.

---

# 16.10. Pricing queue

Сам расчёт может занимать до 30 минут, поэтому важно измерять отдельно **ожидание начала расчёта**.

### Warning

```text
queue wait p95 > 5 minutes
```

### Critical

```text
queue wait p95 > 15 minutes
```

### Действия

Если workers здоровы:

```text
увеличить worker count
```

Если workers перегружены:

```text
scale resources
```

Если очередь растёт быстрее processing rate:

```text
включить backpressure
/
ограничить B2B traffic
```

---

# 16.11. Продолжительность расчёта стоимости

По бизнес-описанию:

```text
обычная модель: 2–3 минуты
сложная модель: до 30 минут
```

Поэтому:

### Warning

```text
calculation > 30 minutes
```

### Critical

```text
calculation > 45 minutes
```

При срабатывании:

- проверить worker;
- complexity модели;
- CPU/memory;
- зависшие calculations.

---

# 16.12. Stuck orders

Самая важная метрика для бизнеса.

Например:

```text
SUBMITTED
более 30–45 минут
без PRICE_CALCULATED
```

требует проверки.

Также необходимо создать alert для заказов, которые рискуют нарушить обещанный клиенту срок.

Компания обещает изготовление приблизительно за три недели.

Поэтому можно определить раннее предупреждение:

```text
заказ не SHIPPED спустя 18 дней
→ WARNING
```

и:

```text
заказ не SHIPPED при приближении
к обещанному сроку
→ CRITICAL
```

Точные значения необходимо согласовать с бизнесом с учётом времени доставки и реальных производственных SLA.

---

# 17. Реакция на превышение saturation thresholds

Alerts разделяются на три класса.

## Warning

Не требует немедленного incident response.

Примеры:

```text
CPU > 70%
DB connections > 70%
queue wait > 5 min
```

Действие:

```text
Monitoring
→ сообщение в командный канал
→ автоматическое создание ticket при длительном сохранении проблемы
```

---

## Critical technical

Примеры:

```text
CPU > 85%
DB connections > 85%
5xx > 5%
consumer = 0
```

Действие:

```text
Monitoring
→ on-call notification
→ incident
→ runbook
```

Если проблема связана с capacity:

```text
autoscaling
```

может сработать автоматически.

---

## Critical business

Примеры:

```text
DLQ > 0
stuck orders
резкий рост failed orders
заказы приближаются к нарушению срока
```

Действие:

```text
Alert
 ↓
Engineering
 +
Product/support
```

Поскольку это уже может непосредственно затрагивать клиентов.

# 19. Ожидаемый результат

После внедрения мониторинга команда должна иметь возможность ответить на следующие вопросы практически сразу:

- Доступны ли Shop, CRM и MES?
- Какой сейчас RPS?
- Растёт ли latency?
- Увеличился ли error rate?
- Перегружен ли MES?
- Хватает ли памяти и CPU?
- Заканчиваются ли соединения с БД?
- Растёт ли RabbitMQ queue?
- Работают ли consumers?
- Есть ли сообщения в DLQ?
- Как долго самое старое сообщение ждёт обработки?
- Сколько заказов находится в каждом статусе?
- Где накапливаются заказы?
- Сколько занимает расчёт цены?
- Сколько заказов зависло?
- Есть ли риск нарушения обещанных клиентам сроков?

Главным результатом мониторинга должно стать не увеличение количества графиков, а сокращение числа ситуаций, когда компания узнаёт о проблеме от клиента.

Мониторинг должен позволить обнаруживать деградацию системы, локализовать её причину и принимать меры до того, как техническая проблема приведёт к потере заказа или контракта.
